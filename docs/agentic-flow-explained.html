agentic-flow

How this agentic flow works

A copy-paste scaffold for running software work across two AI agents and one human, without losing track of intent, evidence, or who is allowed to press which button. One planner, one executor, one owner — and a set of hooks that make the contract mechanical instead of aspirational.

01The shape of it

Most agentic setups fail in the same two places: the reasoning behind a change evaporates the moment the code lands, and the agent quietly does something the human never approved. This scaffold answers both with the same move — separate the roles, and write the design down in a document that outlives the issues.

Work flows one direction. A document states intent. An approved document becomes GitHub issues. Issues become commits. Commits get reviewed, then merged by a human. The document then moves to docs/done/ carrying its own evidence. Issues are disposable; the document is not.

Plan / Review

Claude

Writes the analysis docs and the inlined implementation brief, generates the issues, reviews the execution commits, fixes what the review finds. Commits with git-claude.

Execute

Codex

Implements the issues — one issue per step, one logical commit per step, a regression test per fix. Does not expand scope. Commits with git-codex.

Own / merge / deploy

You

Approves plans before any issue exists, merges the PR, controls every push and every release. Neither agent can push — that's enforced, not requested.

Two agents is the default, not a requirement. A project can opt out (--claude-only) and keep the same document lifecycle and review discipline with a single agent doing both jobs.

02The loop

Everything below is one pass through this cycle. The important property is the approval gate sitting between design and execution: no issue exists, and therefore no code gets written, until a human has read the plan.

The one rule that keeps this honest

The document is the source of design intent; issues are disposable execution units. If the plan changes, you change the document and regenerate the issues — never the reverse. Reverse syncing is how a codebase ends up with no record of why anything was built.

Not everything deserves a full pass

Four delivery lanes. Use the smallest one that still preserves the risk and evidence you need.

LaneUse whenRequired artifact
Fast FixA bounded bug with an obvious approachIssue or short brief, a regression test, one branch/PR
Planned ChangeA feature, security work, or multi-step behavior changeFeature/Security doc, approved brief, one branch/PR per pass
DecisionA product or architecture choice, before implementationProduct Analysis; spin off a Planned Change if greenlit
EmergencyProduction restoration can't wait for planningHotfix PR with evidence, then a retrospective doc

03Documents, and where they live

Four document types, each with a template in docs/templates/. Copy one out — never edit a template in place.

TypeWhat it's forCarries a brief?
SecurityA review or hardening pass. Severity-graded findings, each with file:line and a concrete fix.Yes — inlined
FeatureDesigning a change: goal, current state, approach, and explicitly what not to build.Yes — inlined
Product AnalysisExploratory architecture or product analysis. Options, trade-offs, a recommendation. A decision record.No
ReviewA post-execution architectural review with findings, evidence, and a verdict.No

A document moves through folders as its state changes. The folder is the status — there is no separate board to keep in sync.

Two conventions that make documents scannable

Every document opens with a TRIAGE header — type, status emoji, and one or two lines saying what's current versus historical. scripts/docs-index.sh derives the whole docs/README.md index from those headers, so the index can't rot by hand; --check makes staleness fail the gate.

Every Security and Feature document also carries a tracker near the top — the burndown the executor ticks as commits land:

## Tracker
- [x] SEC-1 Backup restore destroys QA data — fixed in a1b2c3d (#70)
- [ ] SEC-2 KDM expiry only checks start — open (#72)

04From an approved plan to issues

The implementation brief is already an ordered list of independently-shippable steps, so converting it into GitHub issues is mechanical. The plan-to-issues skill does it: one tracking issue for the pass, one sub-issue per step, each carrying that step's definition of done and the exact verification commands.

The labels encode the loop itself: plan on the tracker, then needs-execution, needs-review, agent:codex, agent:claude, and sev:high|med|low|nit for security findings.

05The Makefile is the only source of truth

This is the load-bearing piece that makes the rest stack-agnostic. Every command that builds, checks, or tests the project lives in one Makefile. Humans, both agents, the hooks, and CI all call the same five targets. Nothing hard-codes a raw command anywhere else — so "green locally" and "green in CI" cannot drift apart.

TargetContract
make checkThe fast gate: type-check + lint + harness sanity checks. Cheap enough to run constantly — and the Stop hook does.
make testThe full suite. Must fail loudly when a required tool is missing rather than skipping silently.
make test-one F=…One targeted test, so an agent can iterate on a step without paying for the suite.
make buildThe production build, with dummy CI env values so it never needs real secrets.
make runStart the app locally — what /run and /verify drive to confirm a fix actually behaves.

06Guardrails that don't depend on good intentions

Every rule above is also a hook. An agent that forgets the contract gets stopped by the harness rather than caught in review — which matters most for the rules whose violation is expensive to undo.

Why secret scanning is a commit hook, not a CI job

CI is one step too late. A secret that reaches a commit has to be rotated — rewriting history does not un-leak it. The hook fails at the last moment the fix is still free.

It runs two scanners, always both. Treating the local pattern set as a fallback made the hook weaker on machines that had gitleaks, because its default config allowlists documented sample credentials — a staged AWS example key came back clean and nothing else ran. Any gate whose strength depends on which tools happen to be installed will eventually be green for the wrong reason.

07The commit contract

Identity is enforced by wrapper scripts, each carrying its own SSH signing key: git-claude for the planner/reviewer, git-codex for the executor. The Co-Authored-By trailer is appended by the wrapper, so no one hand-maintains a model name that will go stale.

  • Stage files by name. Never git add -A.
  • One logical commit per step. Don't bundle; don't split without reason.
  • A verbose, why-first body. Name the risk, the approach, the blast radius.
  • Reference the issue with Fixes #N.
  • Never push.

08What CI looks like

Two workflows, because they carry two different risk postures. ci.yml runs on pull requests and cancels superseded runs — a stale run is waste. deploy.yml runs on pushes to release branches and never cancels — finishing a deploy beats half-deploying.

  • Pin everything. Third-party actions by full commit SHA with a # vX.Y.Z comment; runners by version, never ubuntu-latest. A tag is mutable — a SHA is the only pin that resists a compromised action.
  • Steps stay thin. Checkout, set up the runtime, call make. Inlined command sequences are a second source of truth that will drift.
  • The workflow file is its own trigger. Include it in every path filter, so editing CI re-runs what CI gates.
  • Ship the runbook with the workflow — a trailing comment listing one-time server setup and every required secret. That operational knowledge dies otherwise.

09Adopting it

One command installs the harness into a target project. It copies the manifest-declared payload, fills the project name, preserves any differing existing file as <file>.agentic-new instead of overwriting it, applies a stack profile, stamps the scaffold version, and prints the doctor report.

scripts/init.sh /path/to/target-project --name my-project --stack node --yes

# then, inside the target:
scripts/doctor.sh --check
make check

Stack profiles are generic, node, python, go, and rust; detection proposes one from the project's manifests but an explicit flag always wins. CI templates export inert — adoption never activates a workflow behind you, least of all a deploy.

Afterwards, the two things worth doing by hand are filling in CLAUDE.md's Architecture and Gotchas sections as you learn the codebase. Those are what orient an agent in the first thirty seconds of a session, and no scaffold can generate them for you.

10The standards underneath

Process is only half of it. These are the engineering rules the loop assumes, ordered by when they apply.

Automate what a human should never review

Anything a machine can catch must not cost review attention: a formatter and linter that fail the build, strict static typing from day one, dependency scanning blocking on high severity, and secret scanning at the commit boundary. Wire each into make check or make test — never into CI alone, or the feedback arrives after the context is gone.

The ratchet

When a reviewer catches the same class of issue twice, it stops being a review comment and becomes a lint rule, a type, or a test. A review that repeats itself is a missing automation.

Before any code

  • Write the interface first. Signatures, endpoint contracts, data shapes. Most architecture problems are visible here, where they cost nothing, and invisible once there's code attached to them.
  • Threat-model in one paragraph. Who is untrusted, what data matters, what's the worst an attacker could do. Ten minutes, mandatory for anything touching auth, money, or user data.
  • Decide the failure behavior up front for every external call — timeout, malformed response, partial success. Decided during coding, these become guesses no one revisits.

While coding

  • Validate at the boundary, once. Parse external input into a validated type at the edge; interior code then trusts its inputs. Scattered defensive checks never add up to a guarantee and hide where the real contract is.
  • Never build strings that get interpreted. Parameterized queries, argument arrays for subprocesses. This removes most of the injection category by construction rather than by vigilance.
  • Deny by default, at a chokepoint. Per-handler authorization means you will eventually miss one, and the miss is silent.
  • No unbounded anything. Every query has a limit, every loop over external data a cap, every outbound request a timeout.
  • Make illegal states unrepresentable where the language allows it. A type that cannot hold the bad value needs no runtime check and no test.

Verifying and reviewing

  • Test the failure path first. Everyone tests the happy path; the bugs are in the other one.
  • Every bug fix starts with a failing test that reproduces it — it forces understanding the cause instead of pattern-matching a change that makes the symptom go away.
  • Test behavior, not implementation. If a behavior-preserving refactor breaks the tests, the tests were asserting the wrong thing.
  • Small diffs. A 200-line PR gets a real review; a 2000-line one gets a rubber stamp. This is why the loop insists on one issue and one commit per step.
