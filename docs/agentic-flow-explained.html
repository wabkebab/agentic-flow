agentic-flow · standard 0.13.3

How this agentic flow works

A copy-paste scaffold for running software work across three AI agents and one human, without losing track of intent, evidence, or who is allowed to press which button. One planner, one executor, one independent reviewer, one owner — and a set of hooks and checks that make the contract mechanical instead of aspirational.

01The shape of it

Most agentic setups fail in the same two places: the reasoning behind a change evaporates the moment the code lands, and the agent quietly does something the human never approved. This scaffold answers both with the same move — separate the roles, and write the design down in a document that outlives the issues.

Work flows one direction. A document states intent. An approved document becomes GitHub issues. Issues become commits. A separate reviewer judges each commit against the brief. The planner closes out the pass with its evidence, and a human merges. The document then moves to docs/done/ carrying that evidence. Issues are disposable; the document is not.

Plan / Close-out

Claude

Writes the analysis docs and the inlined implementation brief, generates the issues, and after review ticks the Tracker, fills the Status block, verifies the evidence, moves the doc, and closes the tracking issue. Commits with git-claude.

Execute

Codex

Implements the issues — one logical commit per step, a regression test per fix — and comments the commit SHA and the verification it actually ran on the step issue. Does not expand scope. Commits with git-codex.

Review

OpenCode

Reviews each step against the brief. Returns findings to Codex, or posts a structured approving verdict and closes the step. The agent that wrote the code is never the one that judges it. Commits notes with git-opencode.

Own / merge / deploy

You

Approves plans before any issue exists, pushes, merges the PR, and controls every release. No agent can push or merge — that's enforced, not requested.

Three agents is the default, not a requirement. A project can drop Codex (--claude-only; Claude plans and executes) or drop OpenCode (Claude reviews with /code-review or a written review doc, and says the independence is weaker). Exactly one role reviews — an opt-out reassigns the review, it never duplicates it.

Context is loaded progressively. Codex starts from AGENTS.md, the issue, the linked brief step, and the live code. Claude starts from CLAUDE.md plus the template or the Tracker, issue states, verdicts, and CI evidence it needs. METHODOLOGY.md is read by section, never wholesale.

02The loop

Everything below is one pass through this cycle. Two properties matter most. A human approval gate sits between design and execution, so no issue exists and no code gets written until a human has read the plan. And every handoff carries data. A label says who holds the work; the comment behind it says what they are holding.

The one rule that keeps this honest

The document is the source of design intent; issues are disposable execution units. If the plan changes, you change the document and regenerate the issues — never the reverse. Reverse syncing is how a codebase ends up with no record of why anything was built.

Assurance follows the risk

Quick, Standard, and Strict are defined in METHODOLOGY.md §2. The tracked .agentic-flow-assurance file holds the project's minimum; new adoptions start at Standard, and a brief may raise it but never lower it. scripts/assurance.sh reads, checks, and raises it. A downgrade needs --approved-by and --reason and appends to .agentic-flow-assurance-audit. That records a claim for review in the diff; the CLI cannot authenticate who made it.

ProfileWork and artifactReview and evidence
QuickExplicit bounded local work; no formal brief or issueFocused checks and self-check; non-authoritative. Never authorizes a push; promote to Standard before the normal merge workflow.
StandardOne-step Feature brief and one work issue, no parent trackerSeparate-role review, regression test, make check, proportionate broader tests, and CI evidence
StrictFull Feature/Security analysis, tracker, and one sub-issue per shippable stepSeparate-role review and failure-path test per step, full suite, and bound CI and close-out evidence

Strict is mandatory for authentication, secrets, destructive or data-loss behavior, migrations, public compatibility contracts, money, release infrastructure, sensitive data, or an explicit human request. Every profile keeps the same engineering standards, hooks, CI authority, and human ownership of pushes and merges. Decision is a Product Analysis document type; emergency restoration may ship as a hotfix, followed by a retrospective Feature/Security document.

03Documents, and where they live

Four document types, each with a template in docs/templates/. Copy one out — never edit a template in place.

TypeWhat it's forCarries a brief?
SecurityA review or hardening pass. Severity-graded findings, each with file:line and a concrete fix.Yes — inlined
FeatureDesigning a change: goal, current state, approach, and explicitly what not to build.Yes — inlined
Product AnalysisExploratory architecture or product analysis. Options, trade-offs, a recommendation. A decision record.No
ReviewA post-execution architectural review with findings, evidence, and a verdict.No

A document moves through folders as its state changes. The folder is the status — there is no separate board to keep in sync.

Conventions that make documents scannable

Every document opens with a TRIAGE header — type, status emoji, and one or two lines saying what's current versus historical. scripts/docs-index.sh derives the whole docs/README.md index from those headers, so the index can't rot by hand; --check in make check makes staleness fail the gate. A .md file under docs/ outside the lifecycle folders also fails it.

Every Security and Feature document also carries a tracker near the top — the burndown ticked as reviewed commits land — and a Status block that close-out fills with machine-checked evidence (see §05):

## Tracker
- [x] SEC-1 Backup restore destroys QA data — fixed in a1b2c3d (#70)
- [ ] SEC-2 KDM expiry only checks start — open (#72)

Memory: traps that outlive a session

A trap worth keeping lives in docs/memory/ as one file, with one line in docs/MEMORY.md. Agents read the index every session and open a body only when a line looks relevant. Close-out records a memory decision in the Status block, even if it is n/a. scripts/check-memory-index.sh runs in make check. It fails on an entry with no index line, an index line with no file, a path:line citation that no longer resolves, or an index over 50 lines. When an entry keeps proving itself, it graduates into a CLAUDE.md Gotcha or a make check assertion and leaves the index.

04From an approved plan to issues

The implementation brief is already an ordered list of independently-shippable steps, so converting it into GitHub issues is mechanical. The plan-to-issues skill does it. Standard creates one work issue. Strict creates one tracking issue plus one sub-issue per step. Each issue carries an executor packet from the approved brief: brief, definition of done, verification, and risks. The driver rejects a packet over 800 words rather than truncating acceptance criteria. Issue bodies never copy Make recipes; the Makefile owns those.

The label state machine

Labels move in pairs: one agent:* naming who holds the issue, one needs-* naming what it needs. The create-tags skill creates all six with fixed colors; plan-to-issues.sh invokes it only when none exist yet. Reapplying a plan never moves a live step backward. Duplicate or incomplete issue discovery stops before any issue changes.

Anything else — plan on the tracker, sev:high|med|low|nit on findings — gets a neutral gray. The severity scale and the three verdicts (approved, changes requested, pending) are one shared contract, rendered identically into every agent's instructions.

05Close-out and evidence

Because review closes the step issues before anything merges, GitHub issue state can't be the shipping signal. The document's Status block is, and a script checks it rather than trusting it. The v2 schema has exactly eight keys, one per line:

- **Evidence schema:** v2
- **Tracking issue:** url=https://github.com/<owner>/<repo>/issues/93
- **Approval:** status=approved; by=<human>; at=2026-09-20
- **Implementation head:** source=pr-head
- **Implementation PR:** url=https://github.com/<owner>/<repo>/pull/106
- **Verification evidence:** source=final-approval-run
- **Review verdict:** source=pr-head-approval
- **Memory:** status=n/a

Verdicts are structured comments, never free text. Each step issue gets one tied to the executor's full SHA. After the human pushes the close-out commit and CI passes, the reviewer posts a final one on the tracking issue, bound to that PR head and that CI run attempt:

agentic-flow-review: status=approved; pr=106; head=<40-hex>; run=https://github.com/…/actions/runs/<id>; attempt=1; role=reviewer

ACTIVE

Tracker items still open.

UNVERIFIED

Status fields missing, or the external evidence can't be confirmed yet — e.g. no approval for the current head.

BLOCKED

The Status block fails to parse, holds an invalid field, or an authoritative verdict was edited.

READY

Local Status valid and, with --verify-evidence, the issue, PR head, CI run, and verdict author all check out.

scripts/lifecycle-status.sh --doc docs/done/<doc>.md --phase close-out --check --verify-evidence runs before Claude closes the issue. The human runs --phase pre-merge just before merging, which expects the issue already closed. Close-out is the last repository change. Any edit after approval moves the head and restarts the CI and review round.

What verification does not prove

Comments and Actions runs are mutable, so the check is point-in-time, not a merge guard. In single-operator mode the gate authenticates who posted a verdict, but the reviewer role is an attestation, not proof of independence. This repository records that as an accepted risk rather than implying otherwise.

06The Makefile is the only source of truth

This is the load-bearing piece that makes the rest stack-agnostic. Every command that builds, checks, or tests the project lives in one Makefile. Humans, all agents, the hooks, and CI call the same five targets. Nothing hard-codes a raw command anywhere else — so "green locally" and "green in CI" cannot drift apart.

TargetContract
make checkThe fast gate: the stack's type-check and lint, plus harness checks — shell syntax, docs index, payload manifest, root/template contract sync, memory index, action pins, and a fast self-test. Cheap enough to run constantly — and the Stop hook does.
make testThe full suite, plus shellcheck over the shipped scripts. Fails loudly when a required tool is missing rather than skipping silently.
make test-one F=…One focused group, so an agent can iterate on a step without paying for the suite. The scaffold's groups: export, contracts, hooks, plan-to-issues, lifecycle, upgrade.
make buildThe production build, with dummy CI env values so it never needs real secrets. (Here: a dry-run export into a temp directory.)
make runStart the app locally — what /run and /verify drive to confirm a fix actually behaves. (Here: the doctor report.)

Keeping the gate cheap enough to keep

A gate that gets slow gets bypassed, so its cost is measured and budgeted. self-test.sh --fast runs four structural and hook smoke groups with no fixture tree copies. --full runs all six groups from one source snapshot, hard-linking unchanged files into isolated fixtures and copying only the files a test mutates. Each normal run asserts its copy budget, and scripts/measure-harness.sh reports groups, PATH scans, and copies deterministically.

07Guardrails that don't depend on good intentions

Every rule above is also a hook. An agent that forgets the contract gets stopped by the harness rather than caught in review — which matters most for the rules whose violation is expensive to undo. The same hooks are wired for Claude and Codex.

The PreToolUse hooks don't grep command text. A bounded Bash lexer parses words, quoting, separators, environment assignments, and Git global options, then applies one canonical list of commit wrappers. An uncertain protected command — say sudo git add -A behind an unmodeled prefix, or a redirected GIT_DIR — blocks with a value-free diagnostic instead of slipping through. OpenCode has no hook engine in this stack, so the reviewer side of require-step-comment still relies on its agent instructions.

Why secret scanning is a commit hook, not a CI job

CI is one step too late. A secret that reaches a commit has to be rotated — rewriting history does not un-leak it. The hook fails at the last moment the fix is still free.

It runs two scanners, always both. Treating the local pattern set as a fallback made the hook weaker on machines that had gitleaks, because its default config allowlists documented sample credentials — a staged AWS example key came back clean and nothing else ran. Any gate whose strength depends on which tools happen to be installed will eventually be green for the wrong reason. AGENTIC_ALLOW_SECRET=1 overrides a false positive, visibly.

Two agents editing at once need two worktrees

Fanning out is optional; isolation stops being optional once two agents edit at the same time. Without it they share a working directory, and one can stage or overwrite the other's half-finished edit. The Stop gate's stamp is keyed on the whole tree, so a green run would certify the mixture rather than either change. Read-only Explore / Plan fan-outs need no isolation.

The supporting scripts

Creates or reconciles the Standard work issue or Strict tracker and steps from an approved spec, with exact identity matching.

lifecycle-status.sh

Parses the v2 Status block and reports ACTIVE, UNVERIFIED, BLOCKED, or READY; --verify-evidence checks it against GitHub.

assurance.sh

Reads, validates, raises, or (with recorded approval) lowers the project's assurance baseline.

docs-index.sh

Regenerates the docs index from TRIAGE headers. --check keeps it from going stale.

check-memory-index.sh

Keeps docs/MEMORY.md honest: every entry indexed, every pointer and citation still real, the index short.

agentic-flow

The adopter's CLI: offline status, read-only diff, and manifest-bounded upgrade.

self-test.sh

Offline regression suite for the scaffold's invariants, in fast, full, and single-group modes.

Deterministic report of role-context size and self-test work, so cost regressions show up.

08The commit contract

Identity is enforced by wrapper scripts, each carrying its own SSH signing key: git-claude for the planner, git-codex for the executor, git-opencode for the reviewer. The Co-Authored-By trailer is appended by the wrapper, so no one hand-maintains a model name that will go stale.

  • Stage files by name. Never git add -A.
  • One logical commit per step. Don't bundle; don't split without reason.
  • A verbose, why-first body. Name the risk, the approach, the blast radius, and the verification actually run.
  • Reference the issue with Fixes #N — for traceability; review or close-out does the closing.
  • Never push.
Bind session and exchange JWTs to the tenant schema

Signed payloads omitted any tenant identifier, so with a shared secret a
cookie from tenant A verified at tenant B. Add `schema` to every signed
payload and reject mismatches in requireAuth. Legacy missing-claim cookies
are treated as the default tenant for one release to ease rollout.

Fixes #73

Writing that body is not ceremony — it's the review you give yourself. Half the problems in a change surface while explaining it.

09What CI looks like

Three workflow templates, because they carry three different risk postures. ci.yml runs on pull requests and cancels superseded runs — a stale run is waste. deploy.yml runs on pushes to release branches and never cancels — finishing a deploy beats half-deploying. release-native.yml runs on v* tags for stacks that ship a native binary, and is the only one granted contents: write.

  • Pin everything. Third-party actions by full commit SHA with a # vX.Y.Z comment; runners by version, never ubuntu-latest. A tag is mutable — a SHA is the only pin that resists a compromised action.
  • Pin the tools the gate depends on, too. CI installs ShellCheck 0.11.0 from the upstream release, verified against a pinned SHA-256. The runner image's 0.9.0 flagged code that 0.11.0 accepts, so the verdict depended on whatever the image happened to ship.
  • Steps stay thin. Checkout, set up the runtime, call make. Inlined command sequences are a second source of truth that will drift.
  • The workflow file is its own trigger. Include it in every path filter, so editing CI re-runs what CI gates.
  • Ship the runbook with the workflow — a trailing comment listing one-time server setup and every required secret. That operational knowledge dies otherwise.

10Adopting and upgrading

One command installs the harness into a target project. It copies the manifest-declared payload, fills the project name, preserves any differing existing file as <file>.agentic-new instead of overwriting it, applies a stack profile, sets the Standard assurance baseline, records the upgrade source when the scaffold has a git remote, stamps the scaffold version, and prints the doctor report.

scripts/init.sh /path/to/target-project --name my-project --stack node --yes

# then, inside the target:
scripts/doctor.sh --check
scripts/assurance.sh status
make check

Stack profiles are generic, node, python, go, and rust; detection proposes one from the project's manifests but an explicit flag always wins. CI templates export inert — adoption never activates a workflow behind you, least of all a deploy. Watch for a blanket .claude/ ignore rule: it hides the hook configuration from git even though it exists on disk. doctor.sh and agentic-flow status both report git-ignored payload paths.

Staying current

Adopted projects get scripts/agentic-flow, and pull upgrades from the source recorded in .agentic-flow-source:

scripts/agentic-flow status        # offline: version, candidates, adapters, source
scripts/agentic-flow diff          # read-only: what an upgrade would change
scripts/agentic-flow upgrade --yes # apply only files declared in config/payload.tsv

Upgrade follows the same .agentic-new policy as adoption and executes nothing from the fetched standard. .agentic-flow-version (<semver>+<sha>) advances only once no merge candidates remain; until then .agentic-flow-candidate-version records what is pending. It preserves the project's assurance baseline, even under --force. If the recorded origin changes, upgrade stops until you inspect it.

Afterwards, the things worth doing by hand are filling in CLAUDE.md's Architecture and Gotchas sections, and capturing traps in docs/memory/ as you learn the codebase. Those orient an agent in the first thirty seconds of a session, and no scaffold can generate them for you.

11The standards underneath

Process is only half of it. These are the engineering rules the loop assumes, ordered by when they apply.

Automate what a human should never review

Anything a machine can catch must not cost review attention: a formatter and linter that fail the build, strict static typing from day one, dependency scanning blocking on high severity, and secret scanning at the commit boundary. Wire each into make check or make test — never into CI alone, or the feedback arrives after the context is gone.

The ratchet

When a reviewer catches the same class of issue twice, it stops being a review comment and becomes a lint rule, a type, or a test. A review that repeats itself is a missing automation.

Before any code

  • Assess the stack first. Look up current stable releases rather than typing the version you remember, pin them where they execute, and get make check && make test green before building on it.
  • Write the interface first. Signatures, endpoint contracts, data shapes. Most architecture problems are visible here, where they cost nothing, and invisible once there's code attached to them.
  • Threat-model in one paragraph. Who is untrusted, what data matters, what's the worst an attacker could do. Ten minutes, mandatory for anything touching auth, money, or user data.
  • Decide the failure behavior up front for every external call — timeout, malformed response, partial success. Decided during coding, these become guesses no one revisits.

While coding

  • Validate at the boundary, once. Parse external input into a validated type at the edge; interior code then trusts its inputs. Scattered defensive checks never add up to a guarantee and hide where the real contract is.
  • Never build strings that get interpreted. Parameterized queries, argument arrays for subprocesses. This removes most of the injection category by construction rather than by vigilance.
  • Deny by default, at a chokepoint. Per-handler authorization means you will eventually miss one, and the miss is silent.
  • No unbounded anything. Every query has a limit, every loop over external data a cap, every outbound request a timeout.
  • Make illegal states unrepresentable where the language allows it. A type that cannot hold the bad value needs no runtime check and no test.

Verifying and reviewing

  • Test the failure path first. Everyone tests the happy path; the bugs are in the other one.
  • Every bug fix starts with a failing test that reproduces it — it forces understanding the cause instead of pattern-matching a change that makes the symptom go away.
  • Test behavior, not implementation. If a behavior-preserving refactor breaks the tests, the tests were asserting the wrong thing.
  • Small diffs. A 200-line PR gets a real review; a 2000-line one gets a rubber stamp. This is why the loop insists on one issue and one commit per step.
  • One reviewer, by default. A multi-reviewer ensemble is an option for architecture-level or security-critical passes. Aggregation is not a vote: a named arbiter re-checks every high finding and every disagreement against the source.
